Phase 1 · Email analysis

Academic Assistant developer guide

A functional tour of the app for developers joining the project: what each part does and why, which services take part, how data flows during a check, and what ends up in the database.

Audience: developers Companion to the reference docs in docs/

1. What the app does

Academic Assistant is a Windows desktop app that reads a student's university mailboxes, keeps only what matters academically, and turns each relevant email into a small structured record: a category, a priority, the dates it mentions and the course it belongs to.

The problem

A student can have several mailboxes at once, for example an IMAP account at one university and a Microsoft 365 account at another. Exam date changes, assignment deadlines and room changes are buried in the same inbox as newsletters and surveys. Checking every mailbox by hand is slow, and a missed change is expensive.

The mental model

Every "Check now" moves emails through the same six stages. Most of the code you will read belongs to exactly one of them.

  1. SourcesIMAP and Microsoft 365 mailboxes, read-only.
  2. SyncFetch only what is new, using a per-folder cursor.
  3. FiltersDeterministic rules drop duplicates, blocked senders and empty mail.
  4. AI questionsOne structured call per email: typed questions, closed answers.
  5. Structured resultsCategory, priority, flags, course, dates. Saved in SQLite.
  6. UIDashboard, Results and Runs render what the database holds.

Two rules shape everything else. The database is the source of truth: the UI only renders what commands return. And no full email is ever stored: a body lives in memory while one message is processed, then it is gone.

Phase 1 scope

In scope

  • Several accounts, managed from the UI: IMAP and Microsoft 365 (Microsoft Graph).
  • A manual Check now across all enabled accounts.
  • Incremental sync; the first sync covers a configurable number of past days (default 14).
  • Deterministic filters before any AI call.
  • AI analysis of subject and body: relevance, category, priority, action required, possible change, university, course and dates.
  • A manual catalog of universities and courses that helps the AI name the course.
  • New/seen state, search, filters, run history, and logs.
  • Local AI (Ollama) or an explicitly configured external AI (jev).

Out of scope (later phases)

  • Automatic scheduled checks and background execution. Checks are manual only.
  • Native Windows notifications.
  • Linking a message to the earlier one it changes. Phase 1 only sets a possible change flag.
  • Free-text summaries. The AI answers typed questions only.
  • Attachments, Moodle, Blackboard, calendars, web scraping, browser agents, Notion.
  • The final visual design. The current UI is functional, not final.
Where the requirements live

The product requirements are in requirements.md. When code and the original design documents differ, the component documents linked from docs/README.md describe what the code does today.

2. The moving parts

One desktop process holds a React UI and a Rust backend. The backend talks to a handful of outside systems: some over the internet, some on the same PC. This section names each one and says when it is contacted and what happens without it.

Inside the process

src/

React UI in a WebView

Six screens, a typed API client and React Query for caching. It calls backend commands and listens to run:progress and run:finished events. It never calls invoke outside src/lib/api/. Details: frontend/overview.md.

src-tauri

The composition root

Opens the database, builds the adapters and the pipeline runner, registers the commands, validates input, turns domain types into DTOs and forwards run progress as events. It holds no business rules. Details: app/tauri-commands.md.

crates/core

Pure logic and ports

Everything that decides something: the check pipeline, question building, answer assembly, date extraction, filters and text normalization. It performs no I/O and defines the traits (ports) the outside world must implement. Details: core/pipeline.md, core/domain-and-ports.md.

crates/infra

Adapters

One adapter per outside system: SQLite repositories, IMAP, Microsoft Graph with OAuth, jev, Ollama and the Windows Credential Manager, plus the factories that pick an adapter from stored settings. Details: infra/factories.md.

The dependency rule is src-tauri → infra → core. core never imports infra, which is why the whole pipeline can be tested with in-memory fakes. See architecture.md for the crate table and the extension points.

Outside systems and local resources

Each card answers four questions: what it is used for, when the app contacts it, what data goes to it, and what happens when it is unavailable.

IMAP servers internet

Used for
Reading mail of IMAP accounts. Implicit TLS only, usually port 993. STARTTLS is not implemented.
Contacted when
You press Test on an account, and during a check for every IMAP account and each of its folders.
Data sent
Username and password (LOGIN), the folder name and a UID or date search. Mail is fetched with BODY.PEEK[], so nothing becomes read, moved or deleted.
If it is down
Timeouts (20 s to connect, 60 s per command) become a connection error; a rejected login becomes auth. The account fails, the others continue, and its cursor stays put so the next check retries.

infra/imap.md

Microsoft Entra ID internet

Used for
Signing in and exchanging or refreshing tokens (login.microsoftonline.com). The app is a public client using PKCE, with the delegated scopes offline_access Mail.Read User.Read.
Contacted when
During the interactive sign-in, and during Test or a check when the in-memory access token is missing or within 60 seconds of expiry.
Data sent
Client ID, tenant, PKCE challenge and verifier, the one-time code, the refresh token. The user's password is typed in the browser and never reaches the app.
If it is down
A connection error. If the refresh token was revoked or expired, an auth error: "Your sign-in expired. Reconnect the account".

infra/microsoft-graph.md

Microsoft Graph internet

Used for
Reading mail (graph.microsoft.com/v1.0): /me to confirm identity, and the delta feed of /me/mailFolders/{folder}/messages.
Contacted when
Right after sign-in, on Test, and during a check for every Microsoft 365 account and folder.
Data sent
The access token as a bearer header, the folder, a selected list of fields, and a receivedDateTime filter on the first sync.
If it is down
Network problems are connection errors. A 401 or 403 becomes auth: "Microsoft Graph rejected the request. Reconnect the account".

jev API (TypeSafe) internet

Used for
The external structured AI. Only when Settings selects jev.
Contacted when
Once per email that survives dedup and filters, and once on Test provider.
Data sent
Subject, sender name and address, received time, the cleaned body (at most 12,000 characters), the account's default university name, the question texts, and the catalog's course names and aliases. The API key travels in the Authorization header.
If it is down
Rate limits, 5xx and transport errors are retried up to three times (1 s, 2 s, 4 s). If they persist the account stops without advancing its cursor. A 401 or 403 stops it at once.

infra/ai-providers.md

Ollama this PC

Used for
Local structured AI, the default provider. An HTTP server on http://localhost:11434, default model qwen3:8b.
Contacted when
Once per surviving email and on Test provider.
Data sent
The same content as for jev, to the base URL configured in Settings. Keep it on localhost to keep the data on the PC.
If it is down
Connection refused, a 120 s timeout or any non-2xx status (including a missing model) is Unavailable. The account stops and its cursor does not advance. There are no retries.

Windows Credential Manager this PC

Used for
The only place secrets live: IMAP passwords, Microsoft refresh tokens and the jev API key.
Contacted when
Saving an account, signing in, editing the jev key, creating a provider for a check or test, computing "credentials configured", and deleting an account.
Data
Keys such as academic-assistant/account/{id}/password, academic-assistant/account/{id}/refresh-token and academic-assistant/jev-api-key.
If it fails
Commands return "Something went wrong while accessing secure storage"; providers report "Could not read secure storage". The detail goes to the log.

Preconditions

Before anything is written, prepare verifies three things. If one fails, the command returns an error and no run row exists.

  • A single run. A lock allows one run at a time. A second press returns "A check is already running".
  • At least one enabled account. Otherwise: "There are no enabled accounts".
  • AI configured. Ollama always counts as configured (it is only contacted later). Selecting jev without a stored key is refused: "The AI provider is not configured: Add your jev API key in Settings".

The run

  1. You press Check now.The Dashboard calls the check_now command. The button is replaced by a progress label.
  2. The backend prepares the run.It takes the lock, loads settings, lists the enabled accounts (here ids 1 and 2), builds the AI model from the settings, and inserts a runs row, for example id 7 with status running. The model, the settings and the account list are captured at this moment, so editing Settings during the run does not change it.
  3. The command returns the run id immediately.The pipeline continues on a background task. A supervisor task watches it; if the task panics, the supervisor marks the run failed ("Interrupted") and emits run:finished so the UI never hangs.
  4. Account 1 starts.The backend emits run:progress with stage connecting, then asks the provider factory for an IMAP provider. The factory reads the password from Windows Credential Manager. Creating the provider does no network I/O; if the password is missing the account fails right here with an auth error and no folder is touched.
  5. The folder cursor is read.For INBOX there is no sync_states row yet, so the sync is a first sync. The window start is since = now - initial_sync_days, that is 15 September 2026. With a stored cursor, the cursor wins and the window is not used.
  6. Mail is fetched.The IMAP provider connects over TLS, logs in, runs SELECT INBOX and UID SEARCH SINCE 15-Sep-2026, and fetches the matches with UID FETCH ... BODY.PEEK[]. UIDs 501 to 504 come back, parsed into emails and sorted oldest first, together with the next cursor {"type":"imap","uidvalidity":N,"last_uid":504}. At most 200 emails come back per folder per check.
  7. Each email takes the same path.Deduplication and filtering run before any AI call. The diagram below shows every branch; the table after it applies it to our four UV emails.

When things go wrong

The pipeline isolates failures at three levels: a message, a folder, an account. A failure never stops accounts that have nothing to do with it.

The account does not fail. Advances. The message is not retried automatically, because its row now exists.

The dashboard banner for an account is driven by the stored sync state, so it stays until a later check of that folder succeeds. Fixing the cause is not enough; run Check now again. Disabled accounts and folders no longer configured never show a banner.

4. How the AI analysis works

The AI is not asked to write anything. For each email, code builds a list of typed questions with closed answer sets, sends them in one call, validates the answers and converts them to columns. This section explains that design, the questions, the thresholds and what leaves the machine. Reference: core/email-analyzer.md, infra/ai-providers.md.

Why structured questions

jev only answers typed questions, so the whole feature is built around that. The same shape also suits the product: results must be predictable columns the UI can sort and filter, not prose that has to be parsed. There are three question types.

TypeMeaningAnswerUsed for
noulA yes/no statement. The model says how likely it is true.A probability p_yes between 0 and 1relevant, action_required, possible_change
choicePick exactly one key from a closed list of options, each with a description.One option keycategory, university, course, each date
scorePick a level on an ordered scale.A level indexpriority

Every answer is validated against the question that was asked: a missing answer, a key that is not one of the options, or a level out of range makes the call an invalid response. That single email is stored as failed and the run continues (see section 3). The pipeline only knows a StructuredModel port with ask(state, questions); jev and Ollama are two adapters behind it.

What the model receives

The state is a small JSON document. Nothing else about the email is included.

{
  "email": {
    "subject": "Cambio de fecha del examen parcial de Álgebra Lineal",
    "from": { "name": "J. García", "email": "garcia@uv.example" },
    "received_at": "2026-09-29T07:12:00+00:00",
    "body": "Estimados alumnos: el examen parcial se traslada al martes 27 de octubre ..."
  },
  "context": { "account_university": "Universidad de Valencia" }
}

The body is the normalized body: plain text, quoted replies and signature removed, at most 12,000 characters. context.account_university is present only when the account has a default university that exists in the catalog.

The questions

The set is built in a fixed order for every email. Five questions are always asked; the others depend on the account, the catalog and the dates found.

IdTypeAskedWhat it means and how the answer is used
relevantnoulalwaysIs this an academic communication relevant to a student (courses, classes, exams, assignments, grades, schedules, tutoring, academic procedures)? Below 0.4: the email is irrelevant, stored without a result. Otherwise relevant.
categorychoicealwaysOne of notice (general announcement), task (something to complete or submit), exam, event (a talk or session at a time), change (modifies or cancels earlier information), general_info (administrative, no action). Stored as is.
action_requirednoulalwaysDoes the email ask the student to submit, register, reply, attend, prepare, pay or bring something? Flag set when 0.5 or more.
possible_changenoulalwaysDoes it change something communicated before (new date or time, new room, cancellation, new instructions)? Flag set when 0.5 or more. Phase 1 only flags; it does not link to the earlier email.
priorityscorealwaysHow soon must the student act: low (informational, or far away), medium (within weeks), high (within days), urgent (immediate, or within 48 hours). The level chosen is stored.
universitychoiceOnly if the account has no default university and the catalog has at least oneOptions u{id} per catalog university plus unknown.
coursechoiceOnly if there is at least one candidate courseOptions c{id} per candidate course plus none. Each option is described as "Name (University), also known as: aliases", so aliases such as ALG help the model match. At most 254 courses are offered.
date_0, date_1, ...choiceOne per date candidate, at most 20"What does the date written as «27 de octubre a las 10:00» refer to?" Options: exam, deadline, event, class, other, not_relevant.

All questions go out in one call per email. That means an irrelevant email costs the same call as a relevant one, and a malformed answer to any single question makes the whole email failed, even if relevant was clearly low.

Thresholds and derived values

ValueRule
Relevantrelevant.p_yes ≥ 0.4 (constant RELEVANCE_THRESHOLD).
action_required, possible_changep_yes ≥ 0.5 (constant FLAG_THRESHOLD).

How dates are found and classified

Code finds the dates; the model only says what each one is. Calendar arithmetic and year inference are error-prone for language models and easy to test in code, so they never depend on the model.

  • Formats. Numeric (27/10, 27/10/2026, 27-10-2026, 2026-10-27, day first), Spanish and English month names (27 de octubre, October 27), an optional leading weekday, and relative words: hoy, mañana, pasado mañana, próximo lunes, next Monday. "La mañana" and "esta mañana" mean morning and are not dates.
  • Times. Attached to a date when they follow it within 20 characters: 10:00, 10h, a las 10:30, 3 pm.
  • Missing year. The day and month are tried in the previous, current and next year of the email's received date; the closest one that is not earlier than 30 days before the received date wins. If none qualifies, the candidate is discarded.
  • Relative dates are resolved against the email's received time in the local time zone, so the same email gives the same dates whenever it is analyzed.
  • Order and limits. Subject first, then body; duplicates by (date, time) collapse; at most 20 candidates.
  • Classification. Each candidate becomes a date_i question. An answer other than not_relevant creates a row in result_dates with the model's kind; not_relevant dates are dropped.

Detail and examples: core/date-extraction.md.

How university and course are resolved

  1. If the account has a default university, that is the result's university, and no university question is asked.
  2. Otherwise, if the model picked a course, the university of that course wins, because a course is more specific.
  3. Otherwise, if the university question was asked, its answer is used (unknown means none).
  4. Otherwise there is no university.

The candidate courses are the default university's courses when the account has one, otherwise every course in the catalog. An empty catalog therefore means no course question and no course on any result. That is why filling the University catalog improves results.

What is sent outside, and what is not

Privacy

When jev is selected, each email that passed dedup and filters produces one request containing: subject, sender name and address, received time, the normalized body (at most 12,000 characters), the account's default university name, the question texts, and the candidate courses' names and aliases (or the university names, when that question is asked). The date phrases found in the text appear inside the date questions. The API key travels in an HTTP header.

Never sent: recipients (To and Cc), the Message-ID header, provider ids, folder names, attachments, other emails, passwords or tokens. Emails that were filtered out are never sent at all. With Ollama the same payload goes only to the configured base URL.

5. Accounts and sign-in

An account is a mailbox plus the rules for reading it. There are two kinds and they differ in how they authenticate. The provider type is fixed when the account is created.

IMAP accounts

  • Fields. Display name, email, host, port (default 993), username, password, folders (default INBOX), default university, first-sync days (1 to 365, default 14).
  • Where each piece goes. Host, port and username are stored as JSON in accounts.config. The password goes only to Windows Credential Manager under academic-assistant/account/{id}/password. When you edit the account, an empty password field keeps the stored one.
  • Connection. Implicit TLS only (usually port 993); STARTTLS is not implemented. The provider logs in with LOGIN and fetches with BODY.PEEK[], which never sets the read flag. It never moves, deletes or writes anything.
  • Creating one. The account row is inserted, any leftover secret under the new id is deleted (defense in depth), then the password is stored. If storing fails, the row is deleted again. Ids are AUTOINCREMENT, so a deleted account's id is never reused and a stale secret can never be inherited.
  • Providers that block plain passwords. Many universities, Gmail and Outlook.com require an app password or have IMAP disabled. A rejected login is an auth error.

Microsoft 365 accounts

Microsoft 365 mailboxes are read through Microsoft Graph, with OAuth 2 authorization code and PKCE. The app is a public client: it ships no secret.

  1. Register the app once in Entra ID.Multitenant registration, platform "Mobile and desktop applications" with redirect URI http://localhost (any port is accepted, and the app picks a free one at sign-in), delegated permissions Mail.Read, User.Read and offline_access, "Allow public client flows" set to Yes, and no client secret. Full walk-through: setup.md.
  2. Paste the Application (client) ID into Settings.It is stored in the settings table as microsoft.client_id.
  3. Add the account.Fields: name, email, folders (default inbox), default university, first-sync days. The tenant defaults to organizations and cannot be changed later; it must match ^[A-Za-z0-9.-]+$. It is stored as {"tenant": "..."} in accounts.config.
  4. Press Sign in with Microsoft.The flow below runs. Nothing but the refresh token is stored.

Details worth knowing

  • PKCE and state. The app generates a random verifier (its SHA-256 challenge goes in the authorize URL) and a random state. If the returned state differs, the attempt is rejected before any token request.
  • Loopback listener. A minimal HTTP listener binds 127.0.0.1 on a random port and accepts only GET /. Other paths, such as the browser's favicon request, get a 404 and the listener keeps waiting. The whole sign-in times out after 5 minutes.
  • The mailbox must match. After the token exchange the app calls GET /me. The account's email must equal the returned mail or userPrincipalName (case-insensitive). Otherwise nothing is stored and the user sees "Signed in as X, expected Y".
  • Refresh token storage and rotation. The access token is cached in memory and refreshed when missing or within 60 seconds of expiry. Microsoft does not always rotate the refresh token: if the response has none, the old one is kept; if it has a different one, the new one is written to Credential Manager before the new access token is cached. An unchanged token causes no write.
  • What forces a new sign-in. Editing a Microsoft account's email address or its tenant deletes the stored refresh token. A revoked or expired token (invalid_grant) produces "Your sign-in expired. Reconnect the account". In both cases the fix is Reconnect on the Accounts screen.
  • Mail access. Only read permissions are requested (Mail.Read, User.Read, offline_access), so the app cannot send, move or delete messages.

6. The database

One SQLite file holds everything the app remembers except secrets and email bodies. This section shows where it is, how the tables relate, what each table is for and when its rows change during real use. Column-level reference: infra/database.md; the schema itself is crates/infra/migrations/0001_init.sql.

Where the file lives

Folder
%APPDATA%\dev.eaybar.academic-assistant (named after the bundle identifier in src-tauri/tauri.conf.json)
Files
academic-assistant.db, plus -wal and -shm files while the app runs
Created
On first start. The app creates the folder, opens the file, turns on WAL and foreign keys, and applies pending migrations. Reopening an up-to-date file does nothing.
Migrations
Only 0001_init.sql exists. A schema_migrations table, created by the app, records applied versions.

Conventions you will see in the columns:

  • Timestamps are RFC 3339 UTC text, for example 2026-09-29T09:31:04+00:00.
  • Result dates and times (result_dates.date, time) are local YYYY-MM-DD and HH:MM text, exactly what the UI shows.
  • Enums are snake_case text with CHECK constraints. Booleans are 0 or 1. JSON columns (config, folders, aliases, cursor, every settings.value) hold plain JSON text.

The tables

universities

The manual catalog of universities

Key columns

  • id, name (unique), created_at

Relationships

  • Has many courses; deleting a university deletes them.
  • accounts.default_university_id and ai_results.university_id become NULL when it is deleted, so accounts keep working and old results keep existing without a university.

When rows change

  • Created on the University catalog screen (Add university).
  • Updated when renamed. A duplicate name is refused.
  • Deleted from the same screen, after confirmation. The pipeline never writes here; it only reads the catalog once per run.

courses

Courses offered to the AI as answer options

Key columns

  • university_id, name (unique per university)
  • aliases: JSON array of strings, for example ["ALG","MAT101"]

Relationships

  • Belongs to a university; deleted with it.
  • ai_results.course_id becomes NULL when the course is deleted.

When rows change

  • Created, updated, deleted only from the University catalog screen. Aliases are trimmed and blanks dropped.
  • Read at the start of every run to build the course question.

accounts

Configured mailboxes

Key columns

  • id (AUTOINCREMENT: never reused), name, email_address
  • provider_type: imap or microsoft_graph
  • config: JSON without a type tag, {"host","port","username"} or {"tenant"}. No secrets.
  • folders: JSON array, for example ["INBOX"]
  • default_university_id, initial_sync_days (1 to 365), enabled

Relationships

  • Parent of sync_states, run_accounts, processed_messages and ai_results. Deleting an account cascades to all of them, and through processed_messages to results and dates.

When rows change

  • Created by Add account (the password or sign-in secret is stored separately).
  • Updated when you edit the account or flip the Enabled toggle. The check pipeline only reads it.
  • Deleted by Delete account, which also removes both possible credentials.

sync_states

Where each folder stands

Key columns

  • Primary key (account_id, folder)
  • cursor: JSON, nullable. {"type":"imap","uidvalidity":N,"last_uid":N} or {"type":"graph","link":"..."}
  • last_run_at, last_success_at, status (never, ok, error), last_error

Relationships

  • Belongs to an account; deleted with it.

When rows change

  • Created the first time a folder finishes a batch or fails. No row means "never synced".
  • On success: cursor replaced, both times set, status ok, error cleared.
  • On failure: last_run_at, status error and last_error are set. The cursor is left as it was.
  • This table drives the dashboard attention banner. States of folders you removed from the account are ignored.

runs

One row per Check now

Key columns

  • trigger (only manual), started_at, finished_at
  • status: running, success, partial, failed
  • Counters: accounts_processed, messages_found, messages_filtered, messages_analyzed, messages_failed, results_created
  • error_summary, for example "1 of 2 accounts failed" or "Interrupted"

When rows change

  • Created when a check passes its preconditions, with status running.
  • Updated once at the end with status, time, summed counters and summary. At startup, any run still running is set to failed with "Interrupted".
  • Never deleted by the app. processed_messages.run_id and ai_results.run_id reference it without cascade.

run_accounts

How each account fared in a run

Key columns

  • Primary key (run_id, account_id)
  • status: success or failed; the same five counters as runs
  • error_kind: auth, connection, protocol, ai or internal; error_message

Relationships

  • Cascades from both the run and the account.

When rows change

  • Created as each account finishes, whatever the outcome. If the catalog cannot be loaded, every account gets a failed row with kind internal.
  • Never updated. A run that was interrupted may have no rows for accounts it did not reach.
  • The Runs screen joins this table with accounts to show names.

processed_messages

Memory of every email the pipeline looked at

Key columns

  • Unique (account_id, folder, provider_message_id): the "already processed" check
  • message_id_header and content_hash, each indexed with the account: the duplicate check
  • received_at, processed_at, run_id
  • outcome: filtered, irrelevant, analyzed, failed
  • reason: duplicate, blocked_sender, blocked_domain, own_message, empty for filtered rows; a sanitized message (at most 500 characters) for failed rows

No subject, no sender, no body. Only identifiers and a hash.

When rows change

  • Created once per email that is not skipped. Filtered, irrelevant and failed rows are inserted alone; an analyzed row is inserted inside the transaction that also writes the result.
  • Never updated. A processed email is never analyzed twice.
  • Deleted only by cascade when the account is removed, and then its result and dates go too.

ai_results

The structured result of a relevant email

Key columns

  • processed_message_id (unique, one result per email), account_id, run_id
  • subject, sender_name, sender_email, received_at, detected_at
  • university_id, course_id (nullable)
  • category, priority, action_required, possible_change
  • confidence, model_provider, model_name, source_url
  • seen, seen_at; an index on (seen, received_at)

When rows change

  • Created only together with its processed_messages row and its dates, in one transaction.
  • Updated only in seen and seen_at, by the Seen buttons and Mark all as seen (and their undo).
  • Deleted by cascade when the account is removed. There is no per-result delete.
  • source_url is the Graph webLink for Microsoft 365 results and NULL for IMAP. This is the personal-data table: it holds subjects and sender addresses.

result_dates

Dates the model confirmed for a result

Key columns

  • result_id, date (YYYY-MM-DD), time (HH:MM, nullable)
  • kind: exam, deadline, event, class, other

When rows change

  • Created with the result, one per date the model did not call not_relevant.
  • Never updated. Deleted with the result.
  • The "Nearest upcoming date" sort uses the smallest date that is today or later.

settings

Key/value application settings

Key columns

  • key (primary key) and value (JSON text). The keys are listed below.

When rows change

  • The table starts empty; a missing key falls back to its default.
  • Pressing Save on Settings upserts all six keys in one transaction.
  • The jev API key is not here. It is in Credential Manager.

schema_migrations

Applied migration versions

Key columns

  • version (primary key), applied_at

When rows change

  • Created by the app itself when the database opens, not by the migration file. Version 1 is recorded in the same transaction that applies 0001_init.sql.

Unseen results by category

FROM ai_results
WHERE seen = 0
GROUP BY category

8. Security and privacy model

The design goal is that a user can run the whole app without any academic text leaving the computer, and that secrets and message bodies are never at rest anywhere the app controls. Reference: architecture.md.

What is stored where

IMAP passwordWindows Credential ManagerKey academic-assistant/account/{id}/password. Never in SQLite, logs, DTOs or error messages.

Microsoft access tokenMemory onlyCached inside the provider until shortly before it expires; never written to disk.
jev API keyWindows Credential ManagerKey academic-assistant/jev-api-key. The UI can set or clear it and learn whether it exists. It cannot read it back.

What is logged, and what is never logged

  • Logged at info: startup, "check started" with the run id, "account processed" with account id and stage, "check finished" with the status. Every failed command is logged at warn with the command name, error kind, user-facing message and, for internal errors, the internal detail. Command arguments are never logged.
  • Never logged: email bodies and subjects, tokens, passwords, API keys. The Microsoft mismatch error carries addresses for the user, but the log line says only "signed-in account mismatch".
  • Dependencies. In release builds the log filter caps async_imap, hyper, reqwest, rustls and tokio_rustls at warn, because their debug output can include protocol traffic. A RUST_LOG setting cannot raise those crates above warn, although a directive naming a deeper module of one of them can. Treat the log folder as private.

What leaves the machine, and when

DestinationWhenWhat

Nothing else goes out. The React code contains no network calls, and the WebView's content security policy is default-src 'self'; style-src 'self' 'unsafe-inline'; connect-src ipc: http://ipc.localhost, so the UI can only reach the Rust side. In the Rust code, network access exists only in the IMAP, Graph, jev and Ollama adapters and in the loopback listener used during sign-in.

Defensive design

  • Mailboxes are read-only. IMAP uses BODY.PEEK[] and never moves, deletes or flags; Graph is asked for read permissions only.
  • Least privilege in the shell. The Tauri capability grants core:event:default so the UI can listen to run events, and opener:allow-open-url limited to https://*. Nothing else.
  • OAuth hardening. Authorization code with PKCE and a state check, a listener bound to 127.0.0.1 only, a public client with no secret, and a mailbox check before any token is stored.
  • Errors are sanitized. Adapters describe failures in short generic messages (status code, "request timed out", the id of a question that did not validate) and never dump a request or response body. Storage and secret errors reach the UI as generic text; the detail goes to the log.
  • Secrets and ids. Account ids are never reused, so an orphaned secret cannot be picked up by a later account, and a new account's secret slots are cleared on creation.
Working on the code

Never put real credentials, real emails or real personal data in code, tests, fixtures, logs, commits or docs. Fixtures are fictional; tests use fake values such as test-key. This is a rule of the repository (AGENTS.md).

9. Developer tutorial

A hands-on path from a clean Windows machine to a first check you can watch in the logs and the database, followed by how to reset, test and extend the app. Prerequisites and the Entra registration are covered in setup.md; conventions and quality gates in development.md.

1. Prerequisites

  • Rust stable with the x86_64-pc-windows-msvc target and the Visual Studio Build Tools "Desktop development with C++" workload.
  • Node.js 22 or newer and npm. The WebView2 runtime ships with Windows 11.
  • Optional: Ollama for local analysis. A jev API key is only needed if you want the external provider.

2. Run in development

npm install
npm run tauri dev

The Tauri CLI first runs npm run dev, which starts Vite on port 1420 (strictPort is on, so the command fails if something else holds that port). It then compiles the Rust workspace and opens the window. The first Rust build takes several minutes.

Rust under src-tauri/ or crates/Vite ignores these files. The Tauri CLI watches them, rebuilds and relaunches the app. The window closes and reopens, and an in-flight run ends as "Interrupted" at the next start. Data on disk survives.

A check is read-only, but it sends email text to the AI provider you selected. With Ollama that stays on your PC. Do not point development builds at a mailbox with content you would not want to appear in a log or database on your machine.

4. Trigger a check and watch what happens

In the terminal that runs npm run tauri dev the log events also appear on stderr. The same lines go to the daily file. To follow the newest one from a second PowerShell window:

$dir = "$env:APPDATA\dev.eaybar.academic-assistant\logs"
$file = Get-ChildItem $dir | Sort-Object LastWriteTime | Select-Object -Last 1
Get-Content $file.FullName -Wait -Tail 20

You should see check started with a run id, one account processed line per account with stage done or failed, and check finished with the status. To see more of the app's own code, set RUST_LOG before starting, for example $env:RUST_LOG = "info,academic_core=debug". Debug builds do not cap dependency logging, so avoid a bare debug level with a real mailbox, since protocol-level output can include mail traffic.

Then look at the result in three places:

  • The Runs screen: expand the newest run for counters and per-account errors.
  • The Dashboard and Results screens for the new results.
  • The database, using the queries in section 6. Close the app first, or open a copy read-only.

A useful experiment: press Check now twice. The second run should report almost nothing new, because the cursor moved and processed messages are skipped. Then stop Ollama and check again with new mail in the mailbox to see the ai error, the banner on the Dashboard, and the unchanged cursor in sync_states.

5. Reset local state

  1. Close the app (and stop npm run tauri dev).
  2. Delete the data folder %APPDATA%\dev.eaybar.academic-assistant. This removes the database and the logs, so accounts, catalog, settings, runs and results are gone. The next launch recreates an empty database.
  3. Remove the credentials.Secrets are not in that folder. Open Windows Credential Manager, then Windows Credentials, and remove the generic credentials whose names start with academic-assistant/ (IMAP passwords, refresh tokens and the jev key). From a terminal you can list them and delete one by its exact target name: 
    cmdkey /list | Select-String "academic-assistant"
cmdkey /delete:<target name copied from the list>
Destructive

Deleting the folder cannot be undone. Account ids restart from 1 in a new database, so remove old credentials too, otherwise a stale secret could match a new account's id. To re-analyze mail that was already processed, a full reset is the safe route; deleting rows by hand is easy to get wrong because results cascade from processed_messages.

10. Troubleshooting

Start with the Runs screen: expand the newest run and read each failed account's error kind and message. Then check the log file and, if needed, the queries in section 6. The table lists symptoms in the words the UI uses.

SymptomLikely causeFix
Sign-in: "Your organization requires admin approval for this app"The university tenant blocks user consent to third-party apps (AADSTS65001 or AADSTS90094).Ask IT to grant admin consent for the client ID with the three delegated permissions, or use another account or tenant. See setup.md.
IMAP Test or check fails with an authentication errorWrong username or password, IMAP disabled, or the provider requires an app password.Create an app password in the provider's security settings and edit the account. Only implicit TLS (usually port 993) is supported.
IMAP connection error or timeoutWrong host or port, no network, or a VPN is required by the university.Check host and port, connect the VPN, retry. Connect and handshake time out after 20 s, commands after 60 s.

"The AI provider is not configured: Add your jev API key in Settings"jev is selected without a stored key.Use Replace key in Settings, or switch to Ollama.
jev rejects the key, or rate-limits401 or 403 means a wrong or revoked key. 429 is retried three times, then reported.Replace the key. If rate limiting persists, wait and check again; the cursor was not advanced, so nothing is lost.
A run is Failed with "Interrupted"The app was closed or crashed during the run, or the run task panicked.Start a new check. Cursors only advance after a saved batch, so unprocessed mail is picked up again.
A run looks stuck on RunningWaiting on the AI provider (jev 60 s, Ollama 120 s per request), possibly with retries.Wait. If nothing changes, restart the app; the run is marked interrupted.

"Signed in as X, expected Y"You chose a different Microsoft account in the browser.Reconnect and pick the account that matches the email, or correct the account's email.
"Your sign-in expired. Reconnect the account" or "Sign in to this account"The refresh token expired, was revoked, or was deleted by an edit of the email or tenant.Press Reconnect or Sign in on the account.

11. Glossary

Terms as they are used in the code and the UI.

account
A configured mailbox (IMAP or Microsoft 365) with its folders, default university and first-sync window. Table accounts.
attention
The Dashboard list of enabled accounts that need action: a folder whose last sync failed, or a missing password or sign-in.
candidate course
A course offered as an option in the course question: the default university's courses, or all courses when the account has no default.
catalog
The manual list of universities and courses, with aliases, used to help the AI name the course.
choice
A question type with a closed list of options; the answer is one option key.
confidence
A value between 0 and 1 that jev reports per answer. The app stores the minimum across answers and never shows it. Ollama reports none.
content hash
SHA-256 of the lowercased sender, the trimmed subject and the normalized body. Used with the Message-ID header to detect duplicates.
cursor
The stored bookmark of a folder's sync, kept in sync_states.cursor. It advances only after a whole batch is saved.
date candidate
A date mention found in the text by code, with its resolved date and optional time. The model classifies each one.
delta link
The Microsoft Graph URL that returns only changes since the last request. It is the cursor of a Microsoft 365 folder.
duplicate
An email whose Message-ID header or content hash matches an earlier processed email of the same account. Recorded as filtered with reason duplicate.
filtered
A processed-message outcome for emails discarded before the AI: duplicate, blocked sender, blocked domain, own message or empty.
first-sync window
How many past days the first check of a folder fetches. Default 14, from 1 to 365.
invalid response
An AI answer that is missing, has an unknown option or a level out of range. The message is stored as failed; the run goes on.
loopback
The temporary listener on 127.0.0.1 that receives the browser's redirect during Microsoft sign-in.
Message-ID header
The email header that identifies a message across copies. Stored, without angle brackets, for deduplication. IMAP results show it as Copy Message-ID.
noul
A yes/no question type. The answer is a probability of yes, from 0 to 1.
outcome
What became of a processed email: filtered, irrelevant, analyzed or failed.
PKCE
Proof Key for Code Exchange. The sign-in flow that lets a public client exchange a code for tokens without a client secret.
port (Rust)
A trait in crates/core that describes something the outside world provides, such as EmailProvider, StructuredModel, SecretStore or a repository.
processed message
A row in processed_messages: the app's memory that it already looked at an email, and what it decided.
question set
The ordered typed questions built for one email and sent in one call.
refresh token
The long-lived Microsoft token stored in Credential Manager. It is exchanged for short-lived access tokens.
relevant / irrelevant
Relevant when the relevant answer is at least 0.4. Only relevant emails become results.
result
A row in ai_results with its dates: the structured record of one relevant email.
run
One execution of Check now, with a status: running, success, partial or failed. Only one can run at a time (the run lock).
score
An ordered-scale question type. Priority uses it with the levels low, medium, high, urgent.
seen / new
The review state of a result. New results are unseen. The user can mark them seen and undo it.
state (AI)
The JSON document sent with the questions: the email's subject, sender, received time and cleaned body, plus context such as the account's university.
sync state
The stored status of one folder: cursor, last run and success times, status and last error.
tenant
The Microsoft Entra directory an account signs in to. Defaults to organizations and cannot be edited after creation.
UID
The per-folder unique number an IMAP server gives each message. The IMAP cursor stores the highest one fetched.
UIDVALIDITY
An IMAP value that changes when a folder's UIDs are reassigned. If it differs from the cursor's, the cursor is discarded and the window is used again.
WAL
SQLite write-ahead logging mode, which is why -wal and -shm files appear next to the database.
